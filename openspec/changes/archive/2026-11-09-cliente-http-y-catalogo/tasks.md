# Tasks

Plan de `cliente-http-y-catalogo`; esta lista no acredita implementación. Referencias: [propuesta](proposal.md), [diseño](design.md) y deltas de [acceso-a-datos](specs/acceso-a-datos/spec.md), [catalogo](specs/catalogo/spec.md), [datos-locales](specs/datos-locales/spec.md), [libros](specs/libros/spec.md) y [compilacion-y-pruebas](specs/compilacion-y-pruebas/spec.md).

Antes de empezar: confirmar con el usuario las «Preguntas abiertas» de la propuesta. Las tareas siguen las recomendaciones (Catálogo sobre la API y gestión local; autores por detalle con concurrencia 4; sin aviso visible nuevo); si el usuario elige otra opción, se ajustan las specs y las tareas afectadas antes de implementar.

Disciplina (TDD estricto): cada tarea de comportamiento empieza por su prueba fallida (RED observado y registrado: la prueba importa un módulo o una función que todavía no existe, o afirma un comportamiento que todavía no ocurre), sigue con la implementación mínima (GREEN), triangula con un segundo caso y refactoriza con la suite verde. Las pruebas usan un `solicitar` simulado e inyectado: ninguna prueba toca la red (D10). Las vistas y el DOM no tienen runner automatizado: su verificación es la ejecución en navegador, registrando el resultado realmente observado. Registrar en cada tarea el comando y su resultado.

Unidades de trabajo: cada grupo marcado «Commit» es un commit con mensaje de Conventional Commits (sin líneas de coautoría) en la rama `feat/cliente-http-y-catalogo`, con sus pruebas y su documentación. Tamaño orientativo: unas 400 líneas de autoría por commit; si un grupo lo supera, se explica en su evidencia sin partirlo artificialmente. Antes de cada commit, `engram sync` y `git add .engram` (regla dura 16; lo hace el hook `pre-commit` si está activo).

Seguridad operativa: ninguna tarea envía POST, PUT, PATCH ni DELETE a la API de producción; solo `GET`, por el reenvío `/api` del servidor de desarrollo o de la vista previa.
